The guide

Nine stops from a fresh clone to a fleet of checkouts.

The loop people and coding agents run against isolated worktrees. Every stop links into the documentation for exact commands, JSON fields, and configuration.

  1. Register a project by running kwt in it.

    There is no init step. Run kwt inside a repository and it becomes a registered project: the dashboard opens with its primary checkout and any linked worktrees beside the other projects you have registered. A plain directory works too, and becomes a directory workspace with a tmux session and no Git behavior.

    Registration lives in registry.json under KWT_HOME, next to config.toml and pull-request records. Nothing is written into the repository.

    Quickstart · Install · Directory workspaces

  2. Branch into a worktree of its own.

    Press n in the dashboard, or run kwt add -b, to create a branch, its isolated checkout, and its tmux workspace in one move. Your worktrees follow a configured base directory and naming rule, so the checkout lands where you expect without you naming a path.

    Press b, or use kwt add --from, to check out a branch that already exists locally or on a remote. Those worktrees start inert: no hooks, no setup commands, no copied files, no workspace, until you look at them and open them yourself.

    Create or import a worktree · Configuration

  3. Lay out the workspace once.

    Name your agent commands under [agents], compose them into a preset under [[layouts.presets]], and every workspace that selects the preset opens with those panes already running. An empty pane string is a plain shell.

    Layouts are opt-in. Select one with --layout, the L key, or layouts.default; the reserved name none asks for a blank single pane. A repository's own .kwt.toml can set a local default, once you have trusted it.

    Configure a layout · Configuration

  4. Work in it, attached or not.

    A person presses enter or runs kwt open to attach. An agent does not need tmux at all: kwt exec runs a command with the worktree as its working directory, and kwt get resolves the path for anything else.

    Workspaces run on kwt's dedicated tmux server, tmux -L kwt, away from your personal sessions. A terminal client that owns its own attachment asks kwt to establish the session first with --start-session --json and then attaches to the endpoint kwt reports.

    Run and inspect work · kwt open

  5. Read back exactly what changed.

    kwt status summarizes every worktree across projects: branch, dirty, ahead, behind, activity. kwt changes lists the exact changed files in one worktree, staged and working-tree sides separately, with untracked files, renames, deletions, and conflicts.

    Both are read-only. With --json, the result carries the worktree's generation, and you can pass --expected-generation to make kwt fail closed if the checkout you reviewed has since been replaced. kwt list --json is the inventory the rest of your tooling reads.

    Inspect current state · kwt changes · kwt list

  6. Import a pull request behind a protected boundary.

    List a project's pull requests, pass the selected ID back, and kwt creates an inert worktree for it. The contributor branch's exact push destination is preserved, so a fix you push goes where the pull request expects. Repository setup and agent commands stay stopped until you choose to run them.

    Attach only through kwt pr attach. Direct kwt open and the dashboard refuse imported pull-request workspaces; the protected command rechecks the live worktree and its recorded project before it creates or repairs the isolated session on a workspace-specific tmux socket.

    Pull-request automation · kwt pr

  7. Clean up with previews and named stops.

    kwt remove -b removes a worktree and its branch, and refuses when the checkout is dirty or a live process is inside it, naming the process IDs. kwt prune needs an explicit policy, --expired or --merged, and --dry-run shows the complete decision set first. Merged pruning requires a confirmed merged pull request and keeps the local branch.

    kwt doctor finds broken backlinks, stale metadata, and registry drift without changing anything. --fix repairs only findings with one provable answer, rescans, and reports what still needs a person.

    Worktree lifecycle and maintenance · kwt doctor · kwt prune

  8. See your worktrees on every machine.

    Turn on [fleet], point each machine at a hub you run, and every machine publishes its worktree manifest. The dashboard then marks rows that exist only on another machine, heads that differ between machines, and where dirty files were last seen. Select a remote-only row and press s to create the same branch here.

    Sync is advisory by design. kwt never transfers files or commits, clones repositories, deletes remote worktrees, or locks a branch elsewhere. The hub listens on loopback only; put a private TLS endpoint in front of it and keep the bearer token in a file, not in config.toml.

    Multi-machine sync · Sync architecture

  9. Build your own tools on the same lifecycle.

    Start with the CLI and its JSON: it preserves kwt's behavior and exit codes without a client reimplementing daemon discovery. A Go application can construct the inventory, removal, inspection, and SSH services in process from go.kenn.io/kwt. A terminal client that owns its attachment uses the tmux session endpoint.

    Ghosthub embeds these services to manage projects, worktrees, pull-request imports, and tmux workspaces across local and SSH-hosted machines. It is one consumer of interfaces available to any client.
