# v0.5.0 Release Documentation Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Produce human-oriented v0.5.0 release notes and a clear Zensical documentation journey for interactive users, automation users, and embedders without publishing the release tag.

**Architecture:** Keep the existing Zensical site and stable page URLs, but organize its navigation around understanding, starting, using, and integrating kwt. Author the changelog from shipped history, then align first-contact pages, task guides, integration guidance, and exhaustive reference pages to that verified story.

**Tech Stack:** Markdown, Zensical TOML navigation, site CSS, Git history, existing docs asset/build scripts, and Go release checks.

## Global Constraints

- Give interactive developers and automation or agent users equal weight.
- Lead with user outcomes; introduce command names and internal contracts only after the outcome is clear.
- Keep the general Git minimum at 2.20. State that `kwt doctor` plus `kwt prune --expired` and `--merged` require Git 2.31.
- State that source installation requires Go 1.27 and macOS support starts at version 13.
- Preserve existing documentation URLs where practical. New task and integration guides may add URLs.
- Keep exhaustive machine contracts in reference pages and architectural or security rationale in design notes.
- Do not change production code. Stop and request a separate decision if documented and observed behavior conflict.
- Do not add shell tests that assert documentation text. Use the existing strict docs build and inspect rendered output directly.
- Load `kenn:commit` before every commit. Never amend or squash existing commits.
- Do not push `v0.5.0` or create a GitHub release.
- Remove this plan and its design spec from `docs/superpowers/` before the final release-ready commit.
