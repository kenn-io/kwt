# v0.5.0 release documentation design

## Goal

Prepare kwt's documentation for v0.5.0 without publishing the release tag.
The site must explain kwt clearly to developers who work interactively and to
developers who automate work with coding agents. The release history must also
explain how the product evolved to people who do not know its internals.

The work ends with reviewed, verified, committed documentation. Tagging
`v0.5.0` is a separate explicit release step.

## Audiences

The documentation gives equal weight to two primary audiences:

- Developers who use the terminal dashboard to manage worktrees and tmux
  workspaces across projects.
- Developers and coding agents that use stable commands, JSON responses, or
  embedded Go services to manage the same workspace lifecycle.

The v0.5.0 notes also serve embedders. The daemon, public Go services, tmux
endpoints, and SSH facilities are available to clients other than Ghosthub and
must not be framed as private Ghosthub implementation details.

## Editorial principles

- Lead with the reader's outcome. Name commands, data contracts, and internal
  components only after the outcome is clear.
- Define kwt before describing its architecture. Use "Git worktree manager" as
  the category and explain the dashboard and automation interfaces as two ways
  to use it.
- Keep first-contact pages short. Link to task guides, reference contracts, and
  design rationale instead of repeating them.
- Preserve exact command names, compatibility requirements, dates, release
  links, and behavioral contracts.
- Keep exhaustive machine contracts in reference pages. Keep security and
  architectural rationale in design notes and the threat model.
- Remove stale wording, unexplained internal terms, duplicate explanations, and
  implementation detail that does not change how a reader uses kwt.

## Homepage

Use the approved definition-first direction. Replace the oversized slogan with
a compact introduction that answers three questions in order:

1. What is kwt?
2. What does it help a developer do?
3. How can a human or an agent use it?

The opening should describe kwt as a Git worktree manager with a terminal
dashboard and a scriptable interface. Installation and quickstart remain the
primary actions. A real dashboard preview or compact command example supports
the explanation but does not dominate the page.

The rest of the homepage should introduce the interactive and automation paths
as equal uses of the same lifecycle. Safety boundaries and Ghosthub remain
secondary context, not the main pitch.

## Changelog

Rewrite the complete changelog, not only the new release. Each release should
start with a short account of what changed for users and why it matters. The
v0.4.0 and v0.3.0 entries keep their dates, compare links, commands, and factual
scope while adopting the same human-oriented style as v0.5.0.

Create a v0.5.0 release section and restore an empty `Unreleased` section above
it. The v0.5.0 entry groups changes by outcome:

### Maintain worktrees safely

Explain `kwt doctor`, merged pull-request pruning, live-process removal guards,
partial-removal completion, and clear maintenance progress and results.

### Run dependable workspaces

Explain directory workspaces, the dedicated kwt tmux server, faster dashboard
refresh and queued removal, and stable session lookup.

### Automate with confidence

Explain generation-safe `kwt changes`, structured daemon operations and
errors, and guards that stop clients from acting on stale project, worktree, or
session observations.

### Embed and connect kwt

Explain the public Go services, local daemon, reviewed SSH routes, and managed
connection leases as supported building blocks for Ghosthub and other clients.

### Upgrade notes

Call out changes that require action or affect established workflows:

- Bare `kwt prune` no longer performs structural cleanup.
- Maintenance policies require Git 2.31 while the general minimum remains Git
  2.20.
- `KWT_HOME` now isolates registry state as well as configuration.
- Ordinary workspaces move to kwt's dedicated tmux server, with documented
  transition behavior for existing sessions.

Include selected fixes when they affect an understandable workflow, such as
pull-request re-import, partial worktree removal, or branch-stable session
resolution. Do not reproduce the current list of low-level locking and
validation mechanics. Keep those details in the pages that define their
contracts.

## Zensical reader journey

Keep the existing Zensical site and URL structure where practical. Improve the
reader journey with a modest navigation change rather than a site migration.

### Understand

- Rewrite the overview around the approved definition-first homepage.
- Present the changelog as the human history of the project.

### Start

- Tighten installation choices and version language.
- Rewrite the quickstart around shared setup followed by two short, equal
  paths: the dashboard for a person and commands/JSON for automation.

### Use

- Add a worktree and maintenance guide that connects creation, inspection,
  `doctor`, pruning, and removal into one practical lifecycle.
- Rewrite the agent-workspace guide around a dependable automation loop.
- Tighten the directory-workspace guide around its non-Git use case.
- Keep focused pull-request and multi-machine guidance, with clearer entry
  points and less duplicated reference material.

### Integrate

- Add an embedding guide that introduces the public Go services, daemon
  boundary, tmux endpoints, and SSH facilities.
- Keep the CLI and configuration pages exhaustive, but give each a clearer
  orientation and direct links from task guides.
- Retain detailed design notes and the threat model for maintainers and clients
  that need the rationale behind the contracts.

## Cross-site audit

Map every public capability and upgrade note in `v0.4.0..HEAD` to the page where
a reader would expect to find it. Review the homepage, install and quickstart
pages, workflow guides, reference pages, release guidance, navigation, and the
README. Correct stale or missing descriptions and remove conflicting copies.

The implementation should not change production code. If the audit finds a
real conflict between documented and actual behavior, record the evidence and
request a separate decision before changing code or promising a behavior.

## Verification

Run the repository's release checks:

- `make docs-check`
- `make test`
- `make build`

Inspect the rendered site at desktop and mobile widths. Confirm that the
homepage hierarchy is compact, navigation exposes the intended reader journey,
code blocks remain readable, and new pages are reachable. The strict Zensical
build must report no broken internal links or navigation errors. Review the
final diff for stale version references, placeholders, unintended generated
assets, and unrelated changes.

## Release boundary

Commit the completed documentation and report it ready for review. Do not push
`v0.5.0` or create a GitHub release during this work. After the user accepts the
documentation, follow the repository release guide in a separate explicit tag
step.
